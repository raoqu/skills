# Migration Gap Checklist

对每个模块或子模块，至少检查以下问题。

## 范围与入口

- 原项目是否存在多个入口，但 Go 方案只覆盖了其中一个？
- 原项目是否有隐藏入口，例如 cron、queue consumer、admin command、webhook、batch job？
- 文档中记录的入口点是否足够让后续快速回到代码？

## 行为与契约

- 输入输出契约是否与原项目一致？
- 错误语义、重试语义、超时、并发行为是否被遗漏？
- 配置项、环境变量、feature flag 是否还原？
- 数据模型、序列化格式、schema、事件 payload 是否对齐？

## 迁移计划与实施

- `go_migration/plan.md` 是否明确覆盖该模块？
- `go_migration/steps/` 是否真的完成过对应迁移，还是只有计划没有实施？
- `go_migration/` 中是否存在对应代码包、命令、handler、worker、store？
- 现有 Go 代码是否映射错了边界，导致某些职责被错误并入别的模块？

## 验证与风险

- 是否存在与该模块对应的测试或验证证据？
- 是否存在只有 happy path、缺少边界条件验证的情况？
- 是否存在暂时跳过但后续容易忘记的兼容性问题？
- 是否存在跨模块共享逻辑，在迁移时被复制但未统一？

## 继续分析决策

满足任一情况时，建议继续拆子模块：

- 一个模块里混合 API、存储、异步任务三类职责
- 一个模块里有多个几乎独立的入口链路
- 当前模块同时含已迁移和未迁移区域，无法直接判定覆盖
- 当前模块的代码规模太大，不深入就无法形成可靠结论
