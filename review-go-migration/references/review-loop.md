# Review Loop

按下面的顺序执行 review，避免无边界扩张。

## A. 建立顶层模块树

1. 读取原项目运行入口、目录结构、配置和测试布局。
2. 读取 `go_migration/plan.md`、`progress.md` 和相关 `steps/`，了解当前迁移范围。
3. 识别 3-8 个顶层模块，优先按运行职责拆分。
4. 创建或更新 `module-index.md`。
5. 为每个顶层模块创建 `M<n>.md`。
6. 标记哪些模块存在明显迁移遗漏风险。

## B. 深入指定模块

1. 读取目标模块文档。
2. 读取该文档中引用的原项目文件、测试、配置和 Go 实现。
3. 判断是否需要继续拆分为子模块。
4. 生成子模块编号与文档。
5. 回写父模块文档和 `module-index.md`。

## C. 控制读取范围

始终优先读取：

1. `go_migration/docs/migration-review/module-index.md`
2. 目标模块文档
3. 文档中指向的源码与 Go 实现

只在下面情况扩展读取范围：

- 找不到入口点证据
- 无法判断边界
- 现有文档与源码明显冲突
- 需要验证模块间依赖关系

## D. 判断是否继续递归

继续拆子模块的条件：

- 当前模块含多个清晰不同的职责簇
- 当前模块含多个独立入口簇
- 当前模块覆盖多个计划节点且覆盖状态不同
- 不拆分就无法判断哪些部分没迁移

停止递归的条件：

- 当前模块已经可直接映射到一个可审查的迁移单元
- 关键入口、关键行为、关键缺口都已能清楚说明
- 继续拆分只会得到文件级碎片，不能带来更好的迁移判断

## E. 每轮结束必须更新

- `module-index.md`
- 本次新建或更新的模块文档
- 各模块的 `covered/partial/missing/incorrect` 状态
- 下一轮建议继续分析的模块编号
