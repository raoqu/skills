# Software Architecture Recommendations Template

Use this structure for `doc/software-architecture-recommendations.md`.

## 1. 目标与范围

- 用 2-4 句话说明本次建议只覆盖主体技术架构、框架选型与模块边界。
- 明确排除功能细节、页面逻辑、单个业务流程实现。

## 2. 当前架构事实

- 列出当前系统的主要形态，例如单体、模块化单体、前后端分离、monorepo、插件式结构。
- 点名关键目录、入口、框架和运行边界。
- 只写能从仓库直接观察到的事实。

建议格式：

- `事实`：仓库以 `apps/web` + `packages/*` 组织，表现为 monorepo。
- `事实`：Web 层使用 Next.js，服务端能力混在同一运行时中。
- `事实`：领域逻辑同时分布在 `app/`, `services/`, `lib/` 三类目录中。

## 3. 架构判断

- 基于事实归纳 3-5 条关键判断。
- 关注模块边界、依赖方向、框架耦合、数据边界、扩展性和交付成本。

建议格式：

- `判断`：当前更接近“框架驱动的应用结构”，而不是清晰的领域分层结构。
- `判断`：共享代码复用存在，但缺少明确的稳定内核边界。

## 4. 主要问题

按影响度列出 3-6 个问题。每个问题必须说明：

- 现象
- 风险
- 受影响范围

建议格式：

### 问题 1

- `现象`：
- `风险`：
- `受影响范围`：

## 5. 架构建议

按优先级列出建议。每条建议必须包含以下字段，不可省略：

### 建议 1: [一句话标题]

- `优先级`：P0 | P1 | P2
- `针对问题`：
- `建议`：明确说明要调整什么结构
- `落地方式`：给出分阶段做法，优先写 2-4 步增量改造路径
- `预期收益`：
- `代价与权衡`：
- `适用前提`：如果需要满足某些规模、团队或部署条件才成立，就写明

## 6. 建议后的目标架构

- 用短段落描述目标架构，不需要画大而全蓝图。
- 重点说明模块边界、依赖方向、框架角色、共享层和扩展点。
- 如果适合，用一个简短 Mermaid 图表示目标关系。

## 7. 近期执行顺序

- 给出未来 1-3 个迭代内可执行的事项。
- 每项都应该能落成 backlog work item，而不是泛泛方向。

建议格式：

1. 收敛 `src/services` 与 `src/lib` 中的领域入口，先建立单一应用服务层。
2. 把直接依赖框架对象的逻辑从共享模块移出，形成可测试核心层。
3. 为跨模块调用增加明确接口或 facade，减少横向直接引用。

## 禁止输出

- 不要写“建议采用微服务”这类没有迁移条件和成本分析的话。
- 不要只列最佳实践标题，不解释和当前仓库的关系。
- 不要把大量篇幅花在业务功能、页面流程或接口细节上。
