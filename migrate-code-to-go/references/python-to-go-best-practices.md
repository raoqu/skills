# Python to Go Best Practices

当当前迁移节点来自 Python 项目时读取本文件。

## 迁移前先确认

- 入口是 CLI、HTTP 服务、worker、脚本集合，还是库。
- 是否存在 `asyncio`、线程池、进程池、定时任务、消息队列消费者。
- 是否依赖动态行为：monkey patch、装饰器、副作用 import、运行时注入、元类、反射式注册。
- 是否大量使用 `dict`、`Any`、鸭子类型、Pydantic/dataclass/ORM model 作为跨模块契约。

## 结构映射

- 先按原项目的逻辑模块映射到 `go_migration/`，不要先入为主套成统一 `cmd/internal/pkg` 模板。
- 若 Python 项目有明显边界，如 `api/`、`services/`、`repositories/`、`tasks/`，优先在 Go 中保留相近目录语义。
- 对大型 Django、FastAPI、Flask、Celery 项目，先拆出“路由/handler、业务服务、数据访问、任务执行器、配置”这些稳定边界，再分别迁移。

## 语言语义迁移

- 将跨模块流动的动态对象收敛为明确的 Go `struct`、`interface` 和序列化标签。
- 将异常链路改写为显式 `error` 返回；保留原来的错误分类、状态码和可观测信息。
- 将 `None`、空字符串、零值、缺字段区分清楚，不要直接按 Go 零值合并语义。
- 将装饰器、副作用初始化、全局注册，改写为显式初始化和依赖注入。

## 并发与异步

- `asyncio` 代码不要机械翻译为 goroutine；先确认并发目标是吞吐、并发 I/O、任务调度还是超时控制。
- 用 `context.Context` 表达取消、超时和请求级生命周期。
- 对队列消费、后台任务、重试器，先保持原有幂等性和确认语义，再考虑 Go 风格重构。

## 依赖策略

- 对协议客户端、ORM、复杂认证、文档解析、消息中间件等复杂能力，优先评估成熟 Go 库，避免完整自研。
- 对简单工具函数、字符串处理、集合变换、轻量日期工具，不要为了接近 Python 生态额外引入依赖。
- 若原项目严重依赖框架魔法，先在 `docs/analysis/` 写清框架帮你做了什么，再决定 Go 落地方式。

## 验证重点

- 校验序列化格式、时间精度、默认值、缺省字段行为。
- 对脚本或批处理，比较退出码、标准输出/错误输出和副作用文件。
- 对 Web 服务，比较路由、状态码、错误体和中间件顺序。
- 对数据层，重点核对事务边界、懒加载/预加载行为、批量写入语义。
