# Java to Go Best Practices

当当前迁移节点来自 Java 项目时读取本文件。

## 迁移前先确认

- 项目是 Spring Boot/Jakarta EE 服务、普通库、多模块 Maven/Gradle 工程，还是批处理/桌面程序。
- 哪些能力来自框架自动装配、AOP、注解、过滤器链、事务代理，而不是业务代码本身。
- 是否存在 JPA/Hibernate、MyBatis、消息中间件、定时任务、线程池、缓存、分布式锁等基础设施。
- 多模块工程之间的依赖边界和公共模型是否已经清晰。

## 结构映射

- 优先保持原包结构背后的业务边界，例如 `controller/service/repository/client/job`。
- 不要机械把 Java 的每一层都压成少量 Go 文件；在 `go_migration/` 中保留可追溯的目录语义。
- 对 Maven/Gradle 多模块工程，先在计划中明确哪些模块会合并、哪些会保留分界。

## 语言与框架语义迁移

- 将继承层级、抽象基类、框架注解行为改写为组合、显式接口和初始化流程。
- 将异常体系改写为显式 `error` 返回，同时保留原有错误分类、错误码和日志上下文。
- 将 Spring Bean 生命周期、拦截器、事务、配置绑定、条件装配等行为先写入分析文档，再实现 Go 对应机制。
- 将 Java DTO/Entity/ViewModel 的边界在 Go 中继续保持清晰，不要因为结构相似就全部复用一个 `struct`。

## 并发与资源管理

- 将线程池、`CompletableFuture`、调度器、反应式流先还原为执行模型，再决定 Go 中的 goroutine、channel、worker pool 或同步控制。
- 明确连接池、事务、上下文取消、优雅停机和资源释放逻辑。
- 若原实现依赖线程本地变量、过滤器上下文或拦截器链，迁移后要找到显式传递方式。

## 依赖策略

- 对 HTTP 客户端、数据库驱动、消息队列、认证、对象存储、复杂文档解析等复杂模块，优先评估成熟 Go 库。
- 对简单工具类、POJO 组装、轻量转换器，优先直接迁移或用标准库完成。
- 若决定放弃某些 Java 框架特性，必须在 `dependency-mapping.md` 和步骤记录中说明行为差异。

## 验证重点

- 对 API 服务，比对路由、状态码、错误体、事务边界、过滤器顺序和配置默认值。
- 对数据层，比对 SQL、分页、排序、事务传播、懒加载/预加载差异。
- 对消息和调度任务，比对消费语义、重试、并发度和幂等性。
- 对多模块工程，比对模块间契约、配置装配和启动顺序。
